# 工程 UUID 与合同工程编号规范设计

日期：2026-08-18

## 目标

- 新建工程使用标准 UUID v4 作为不可变内部主键。
- 页面不再向用户展示随机内部主键，统一展示有业务含义的工程编号。
- 人工填写内部管控编号时优先使用；未填写时按建档日期自动生成 `YYYY-MM-NNN`。
- `NNN` 表示全公司该自然年度第几号工程合同，跨月份连续、每年从 001 重新开始。
- 已有工程 ID 和工程编号保持不变，不做破坏性迁移。

## 方案比较

### 方案一：直接把合同编号作为数据库主键

不采用。合同编号可能补录、修改或来自甲方，直接修改会破坏档案、回款、生产、日程和审批的关联。

### 方案二：前端统计并生成顺序编号

不采用。多个用户同时建档时可能读取到相同最大序号，无法保证全公司编号唯一。

### 方案三：UUID 内部主键与服务器顺序工程编号分离

采用。服务器生成 UUID v4，并在数据库事务内分配年度序号；内部主键保持稳定，工程编号负责展示和检索。

## 数据规则

1. `Project.id`：服务器生成 UUID v4，仅用于内部关联。
2. `Project.code`：用户可见工程编号。
3. 新建工程填写 `internalContractNo` 时，`code` 使用该值。
4. 未填写 `internalContractNo` 时，服务器按建档时间生成 `YYYY-MM-NNN`。
5. `contractNo` 继续保存甲方合同编号，不参与内部主键。
6. 年度序号按所有新建工程递增，不因月份变化重置；年份变化后从 001 开始。
7. 自动编号和人工内部管控编号都必须全局唯一；冲突返回 409，不静默覆盖。
8. 工程编号和建档时间生成后不可修改；需要补充甲方合同号时使用独立的 `contractNo` 字段。

## 服务端设计

- 新增年度工程编号序列表，以年份为主键保存最后分配序号。
- 迁移时根据现有工程的建档年份初始化年度计数，但不改写历史工程。
- 工程创建使用数据库事务：先锁定全局建档哨兵行，再锁定或原子递增年度序号、生成 UUID、写入工程记录，一次成功或整体回滚。
- 工程创建接口返回服务器最终保存的完整工程对象；客户端不得自行决定正式 ID 或自动编号。
- 服务端校验人工内部管控编号和最终 `code` 的唯一性。

## 前端设计

- 新建工程不再使用 `Math.random()` 生成工程 ID 或 `PJ-年份-随机数`。
- 等待服务器成功返回后再把工程加入列表，避免临时 ID 污染关联数据。
- 回款详情中的“工程 ID”改为“工程编号”，显示 `project.code`。
- 工程列表和流程页继续显示 `project.code`；现有工程展示不受影响。
- 创建失败时保持表单并显示明确错误；编号冲突提示用户修改人工编号或重试。

## 测试与验收

- UUID 符合 RFC 4122 v4 格式。
- 同年连续建档生成 `001`、`002`，跨月继续递增，跨年从 `001` 开始。
- 并发创建不会产生重复编号或重复 ID。
- 人工内部管控编号优先，重复编号返回 409。
- 现有工程 ID、档案、回款、生产和日程关联保持不变。
- 页面不再显示内部随机 ID，改为显示工程编号。
- 完整测试、TypeScript、生产构建、依赖审计和发布门禁通过。
